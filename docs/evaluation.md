# Experimental methodology and interpretation

Experiments consume deterministic workload payloads generated by Mersenne Twister with recorded seeds. The *real* verifier never receives attack labels; these are retained by the measurement driver only. `results/raw/` files contain observations from execution, with a backend column.

E1: AT1, AT6, AT8 and late-after-revocation AT7; E2: AT2, AT3, AT4, AT10; E3: per-event anchor call counts and separately timed construction, anchoring, and verification; E4: physically paced batch-size/rate tests with genuine monotonic event-to-anchor delay (the memory backend is still not Ethereum); E5: pre/post revocation and valid rotated epoch; E6: internally consistent fake AT9 events with stolen key and genuine signed clock-skew AT5; E7: process timing and RSS stability.

A randomized payload seed is **not an independent draw from a population of cryptographic attack success outcomes**. Detection and security results are a deterministic observed pass/fail matrix, stratified by naive versus adaptive attacker model. No Clopper–Pearson confidence bounds, McNemar p-values or Holm significance tests are assigned to these outcomes. Bootstrap timing intervals are descriptive for the sampled trials, not claims about external machine populations. External validity requires independently replicated environments and frozen adversarial configurations.

In-memory measurements establish Python protocol behavior, not blockchain costs. EVM measurements require live Anvil and must be evaluated in multiple independently reset local chain sessions under controlled CPU/power conditions. If a separate session cannot be reset fairly, record that as a confounder. E3's 10,000 per-event B1 cap is transparent; extrapolations beyond executed transaction counts are not reported as observations.

### Required external validation before publication

- Compile and execute Foundry tests with a pinned compiler release.
- Run actual EVM ledger experiments, verify the receipts and archived contract bytecode/ABI.
- Freeze configuration grids with attack rates, stream volumes, batch sizes and order randomization; perform the full replicated study, not only this smoke/pilot runner.
- Independently audit crypto design, contract, key lifecycle, storage rollback, and canonicalization interoperability.
- Compare against validated contemporary secure-logging systems, not only internal ablations.
- Review benchmark stability and contradictory/negative results, with machine-specific environment manifests.

### Evaluation restrictions after security review

E1 now distinguishes naive archive mutations from adaptive unsigned commitment recomputation; B3 can accept adaptive content substitution. E2 includes an explicit *anchored-tail-truncation* condition. These are negative results when a component fails to differentiate methods; never discard them. The harness still does **not** establish an advantage attributable solely to the hash chain over sequence-bound signed Merkle commitments, and no such novelty is claimed. It does not include an independently validated published external baseline.

The E3/E4 Anvil harness randomizes method order, but does **not** reset the local chain between methods. Each Anvil result is marked `chain_reset_before_method=false`, meaning chain-history/order bias is unresolved and journal-grade per-method comparisons must be repeated under separately reset Anvil deployments. Source timestamps vary deterministically; synthetic traces are not an empirical enterprise workload. No `uv.lock` was generated in the offline development environment. A future online lock generation and dependency audit are prerequisites for exact environment reproduction.
